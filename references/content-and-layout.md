# 设计交付内容与排版规则

## 前置文案必须纵向排列（强制）

- 项目背景、问题/设计难点、设计目标、设计策略等前置说明，必须按阅读顺序自上而下排列。每项标题在上、正文在下，标题与正文同组；各组左边缘对齐。
- 禁止把这些前置说明改为横向多列、三栏摘要或并排卡片；不得以压缩画板高度、右侧有空位或“先横排”为理由横排。只有用户本轮明确要求前置文案横排时才可例外。
- Figma 使用纵向 Auto Layout，正文随内容换行，容器 Hug 高度；HTML 使用对应的单列结构。字号、行高和间距继承已确认模板；文案可用宽度跟随画板左右留白，写到内容区右边缘自然折行，不使用任意固定窄框限制正文。
- 交付验收必须单独检查：前置说明各组纵向排列、同一左边缘、每项标题紧随其正文之前；未通过不得报告完成。页面方案区仍按二维布局组织，不受本条限制。

## 交付画板内容与页面顶对齐（强制）

- 前置说明使用普通文本，禁止套可见卡片、边框或固定宽高裁切框。文本使用 Auto height，宽度为画板宽度减左右留白；到右边缘自然折行。辅助 Auto Layout 仅用于纵向组织，必须无填充、无描边、无裁切、Hug 高度，不得用 Auto width 让长文越界。检查全文可见，不能只关闭裁切让文字溢出画板。


- 交付画板面向老板评审和开发交接，只保留产品背景、设计策略、页面/状态标题、业务规则与必要交互说明。
- 禁止展示 Agent 工作过程：需求核对清单、修改记录、执行计划、验收报告、工具/节点说明、自我解释、“已同步/待补/尚未验收”等过程文案。这些内容留在聊天或工作记录，不放上交付画板；确需决策的业务问题用简短明确的问题表达。
- 每一横排必须对齐实际页面顶边，不只是外层分组或标题顶边。页面上方标题、说明高度不同，应整理为统一标题区或调整交付容器，保证同排页面起点一致。禁止垂直居中、底对齐或 Space Between 导致页面错位。
- 交付前逐行检查真实页面的绝对 Y 坐标，再看整板截图；不得只凭 Auto Layout 设置声称顶对齐。前置背景、难点、策略仍必须纵向排列。

## 先确定本次改什么

先读用户当前要求、指定节点和最近确认的结果，再读相关规则。将要求理解为对现有成果的增量修正；不能用最后一句话覆盖此前仍有效的确认。

写入前在工作记录中简要确定：目标对象、参考来源、允许变化、必须保留的内容、可观察的通过条件。记录不放进交付画板，也不让用户批准常规判断。

- 产品 UI 先使用 `ui-quality-gates`，按模板继承 → 系统组合 → 探索的顺序判定。参考和已确认成果存在时，复用真实结构。
- 先区分此次对象：产品页面内部、页面外的状态补充、交付画板外壳，或交互原型。要求修改其中一层，不自动授权修改其他层。
- 已确认的文字、数据、状态、数量和交互含义构成保留清单。重新分组、补充状态或修边缘，不得顺便改掉它们。若当前稿已经偏离用户确认，按有证据的确认版本恢复，不把错误现状当新基线。
- 用户要求“搬过来”“保留这一组”，先确定其批准的是内容、产品结构还是外层排版；不得自行删状态，也不得默认临时检查稿的底板、检查标题、调试说明都属于正式交付内容。当前用户明确要求外壳原样保留时，以该要求为准。
- 通用 skill 只保存跨项目的判断方法。具体业务规则、卡片数量、某屏露出比例、节点位置和本轮排法写在项目规范或任务记录；不得将一次修正推广为所有页面的默认行为。
- 继续已有项目时，定位真实源文件与打包入口。修改源文件后重建受影响的已交付版本。仅要 Figma 时不额外生成 HTML；要可转发 HTML 时默认交付可直接打开的文件。

## 内容职责与空间组织

先按“读者需要理解什么”分组，再决定摆放位置。以下是内容职责，不是必须凑齐的目录或固定三行布局。

| 内容 | 要回答的问题 | 排版和连线 |
|---|---|---|
| 主页面与设计说明 | 页面如何组织，为什么这样设计 | 主页面先行；说明紧贴对象 |
| 并列状态 | 同一页面或模块在不同条件下是什么样 | 并列比较；不把状态集合串成操作步骤 |
| 操作或跨页路径 | 从哪里触发，到哪里，如何返回 | 独立标题或就近局部标注；只连必要的代表路径 |

- 状态即使能由点击触发，也不自动成为跨页流程。页内操作前后可就近标注；其他状态独立平铺，不从路径末端逐一拉线。
- 必要跳转在首次完整说明该行为的位置画一次。核对整卡、行、图标等真实入口，不能只找文字按钮。重复入口不重复拉线。
- 上游来源是否展示完整页面，取决于本次交付范围；用户举的路径示例不自动成为整张交付板的开头。
- 同级方案并排；方案下的方向就近并列；公共内容独立分组。若只展示局部状态，将它放在对应页面旁并对齐原模块锚点。用户已指定独立状态区的位置时，以该位置为准，不机械搬回页面旁。
- 按各组真实宽高安排二维布局。右侧能合理容纳下一组时，不无故另起整行；也不为填空打散语义完整的组。
- 背景、目标和说明使用面向业务与开发的项目语言。不加内部来源免责声明、执行过程或未确认事实。历史版本与当前口径分开。

## 用规则表达交互

- 交付说明描述可复用的行为规则，示例只用于演示。说明应让读者判断规则何时适用、如何触发、产生什么结果，并能应用到未展示的实例。
- 相同行为用一条代表路径说明；只有规则存在差异时，才补充分支。展示多少实例不决定需要多少规则。
- 规则应明确到足以指导实现，但不绑定演示数据。按已确认的交互边界描述，不为简化表述改变实际行为。
- 验收时检查两点：换一个实例，规则是否仍然成立；没有展示该实例，读者是否仍能判断其行为。不能成立时，优先补足适用条件或行为差异，而不是继续增加实例。

## 总览中的设计策略与汇报文字

设计策略用自然、专业的完整句子说明具体做法及必要理由。精简是删除重复和空话，不是将句子缩成“机会按天看”“票券折叠看”这样的口号。总览保留整体方案的核心判断，状态枚举、展开过程和例外说明放到对应页面旁；不要用一句口号加一段重复解释制造篇幅。

撰写或改写这类文字时，遵循 [humanizer-zh 的汇报与设计策略规则](../../humanizer-zh/SKILL.md#汇报与设计策略的写法)。检查读者能否直接理解改了什么、为什么，以及必要的条件；不强凑短句、排比、字数或条目数。文案变短不等于意思更清楚，不能删掉理解方案所需的信息。

## 复用内容时分清两套样式

产品页面和交付外壳有各自的模板。复用时分别确认来源，不用其中一套替代另一套。

1. **产品本体**：真实页面、卡片、弹层等。保留其内容、内部层级、尺寸、字体、背景、圆角与交互状态。
2. **交付外壳**：章节标题、状态标签、说明、组间距与画布背景。使用当前交付模板；标签与对应页面或模块组成可一起移动的容器。
3. **临时检查外壳**：用于开发、检查或临时摆放的底板、测试标题、内部说明。不能仅因与产品内容处于同一父节点就带入正式交付。整理时只处理外壳，保留产品本体，并保留原参考稿。

白色或其他颜色本身不是错误。先追踪背景属于哪一层，再决定保留或移除；不能全局去白、去色、清空填充或把整组截图当作可编辑模块。

项目标题栏的高度、图标、字号和署名应随当前整张画板的规模协调缩放，不沿用宽大母版的固定尺寸；完整保留作者信息，并按 [标题栏与整板比例](delivery-visual-style.md#项目标题栏与整板比例) 验收。

排版先按内容归属建组，组内距小于组间距；标题在视觉上必须更靠近其下正文。执行 [内容归属与就近排版](delivery-visual-style.md#内容归属与就近排版)，交付前主动逐组检查实际字形间距与换行后的归属，不能只验文本框 gap。

标题须有明确的对齐对象：章节标题对齐所属内容组，状态标签对齐其模块；同级使用同一文字样式、对齐方式和标签到内容的间距。检查文本框与实际文字的左边缘、垂直位置及换行，不能只看 x/y 相同。换行需要一致的排版处理，不任意缩字。

## 修缺陷而不改变正确行为

先根据参考与当前要求判断异常，再追踪实际负责的背景、尺寸、padding、滚动视口、遮罩或裁切层。修改导致缺陷的层，不通过改内容、删状态、遮盖或全局关闭裁切消除表象。

- 溢出与有意露出不能混为一谈。滚动、轮播、叠层等可能有有意裁切；是否正确由该页面已确认设计决定，skill 不规定露出数量或比例。
- 背景边界、内容可视窗口和交互范围分别检查。修一个边界时，不连带改变其他已确认行为。
- 内容删除、折叠或移到侧面说明后，页面、背景及交付容器应随实际内容收缩；同步重排后续模块和组间距，不保留旧高度的空壳。先区分内容长页与固定设备视口，按 [内容变化后的自动伸缩](figma-board-delivery.md#内容变化后的自动伸缩) 验收；不能把去掉遗留空白误判为裁切正文。
- 修改后对照保留清单复核影响范围；若相邻内容变化，解释其必要性或恢复。新错误不能成为下一轮参考。

## 交付验收

验收条件须来自本轮要求，不能用“已检查”“无溢出”代替实际结果。

- **内容**：确认的状态、数据和页面齐全；无擅自改动或检查文案泄漏。
- **结构**：产品本体与外壳归属清楚；标题、标签和模块同组；布局关系由 Auto Layout 或对应 CSS 表达。
- **整板**：分组、阅读顺序、横向空间、连线和页面归属可读；没有为修局部而破坏既有排法。
- **连线**：逐根核对真实点击入口、目标对象和必要的点击说明；重排后重新校准受影响的线与标注。Figma 按 [每根连线的语义与位置验收](figma-board-delivery.md#每根连线的语义与位置验收) 执行，不以线条存在或样式正确代替关系正确。
- **局部**：在可辨认文字和边缘的尺度，核对受影响区域的背景归属、标题对齐/换行、裁切及交互提示。
- **实际交付物**：检查最后修改后的用户所见画板或重新打包的文件。节点存在、复制成功、导出成功、图片有 alpha 通道都不是视觉通过。编辑器与导出不一致时，继续排查，不能只用正常的导出图宣称修复。

未通过的检查继续修复；无法验证的范围明确说未验证。不得将 skill 文本校验通过当成设计交付通过。
